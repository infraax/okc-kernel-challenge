## 1. The key question: does `_full_kernel` (verify-full) issue cp.async?

**Yes.** `kernels/muse_attention_decode/sonnet_v3.py`, `_full_kernel` (verify, q_len 8: `num_warps 4, num_stages 4`): **cp.async = 32**, ld.global = 28, ldmatrix 8,
wgmma 18, ex2 84, regs 185, spills 0, smem 69 632 B; its `cp.async.wait_group` values are `0x1,8x1` (a wait that leaves 8 copy groups in flight: the K / V copies of
the next tiles stay pending while the current tile is computed). Its docstring (cp.async pipeline, page ids carried in registers, K / V rows requested 2 tiles ahead) matches the PTX.
`_full_cat_kernel` (decode): cp.async 36 (4 warps, batch 1) / 72 (2 warps, batch 16 / 32), `wait_group 2` (3 tiles deep). Sliding `_attn_kernel`: cp.async 27 (decode) / 19 (verify) at
`num_stages 3`; 0 only where the file itself passes `num_stages=1` (short splits).
=> fable-09 D7's trigger "`_full_kernel` shows 0 cp.async" is **false**; its own fall-through is "close C26' as pipelined" (the director decides; this file only reports the count).

## 2. "pipelining silently inert" (num_stages > 1 with 0 cp.async and a dynamic loop): **none** in the audited files

`#F` lines of the tool: none for `sonnet_v3` attention, `sonnet_v4` decode layer, `director_v1b`, `sonnet_v4` MoE. Every Triton kernel with `num_stages > 1` and a `range()` loop has
cp.async > 0 and a non-zero `wait_group` (rows below). Kernels with `num_stages` 3 by Triton's default but no dynamic loop (`_epilogue_kernel`, `_local_ids_kernel`: only `tl.static_range`) are
marked `loop n`: the stage count is irrelevant there.

**Why fable-09 [F1] ("Triton 3.8 emits no cp.async for our plain-load K loops", `tools/ptx_probe_gemv.py`) looked true and is not:** the probe compiles with `ASTSource(fn, signature, constexprs)`
and NO divisibility attributes, so every pointer and stride is "unknown alignment": Triton cannot vectorise to 16-byte accesses, falls back to plain `ld.global` and never emits cp.async.
The real launch (`JITFunction.run`) adds `tt.divisibility = 16` for every 16-byte-aligned pointer and every int divisible by 16 (K = 8192, strides, N), and then the same kernel IS pipelined.
`tools/ptx_audit.py --align none` reproduces the probe exactly; `--align real` (default) is what the judge compiles:

| `_gemv_splitk` router m 1 (`BN 64, BK 128, SPLIT 16`, 4 warps, 4 stages) | regs | spill B | smem B | ld.global | cp.async | wait_group | mma.sync |
|---|---|---|---|---|---|---|---|
| `--align none` (= ptx_probe_gemv.py, **not** the judge) | 255 | 920 | 12 288 | 144 | **0** | - | 32 |
| `--align real` (= the judge) | 128 | 0 | 110 592 | 0 | **72** | `0x1,6x1` | 32 |

Consequences for the plan: [F1] and the `TMAPOOL` / "force the pipeline" rows that rest on it have no PTX basis; the plain-load GEMV already has a 3-4 stage cp.async ring (the pooler
`BK 512, BM 16, BN 32` config reserves 147 456 B of shared memory, i.e. one CTA per SM; the m 32 pooler 131 072 B). Whether the ring is deep enough for the bytes in flight is a
measurement question (Little's law), not a "0 cp.async" question. The "known fact" asserted by the old probe is kept as a test of the `--align none` mode only
(`tests/test_ptx_audit.py`).

## 4. Method and limits

* The tool runs the file's own host code on the dev GPU (RTX 2060: only Triton's driver is used, nothing is launched) with `torch.cuda.get_device_capability` -> (9, 0) and
  `JITFunction.run` patched to record (arguments, Triton's own specialisation, constexprs, options, grid). Inputs are shaped like the scored cases of `problems/<p>/TASK.md`
  (caches are `torch.empty`). So the configs are the ones the file really derives for those shapes, including shape-dependent ones (`_plan`, `_plan_full`, `_CFG` buckets).
  Each distinct (kernel, constexprs, argument types incl. 16-divisibility / ==1 specialisation, options) is compiled once; identical metrics are merged (`nodiv16=<args>` in a label
  names the arguments that are not divisible by 16 when that changes the code, e.g. M = 8 vs 16).
* decode layer v4 and MoE v4 need SGLang (Marlin, FA3, routing) for their full `kernel_fn`; the driver calls the file's Triton stages directly with the judge's dispatch
  (`_router_path`, `_pooler_path`, `_attention_decode`, `_marlin_knobs`, `config_for`): the cuBLAS / Marlin / FA3 / SGLang-fused kernels are not Triton and not audited.
  `_router_f2_kernel` is switched off in the file (S2) and is reported as dormant. M >= 32 tokens use SGLang's fused epilogue on the judge, so the Triton epilogue appears only below 32.
* `spills` for Triton kernels = ptxas `spill stores + spill loads` in bytes; for NVRTC kernels = cuobjdump `LOCAL` bytes (spills + local arrays; an upper bound). `smem` = dynamic
  shared bytes Triton reserves; for NVRTC kernels the static shared bytes only (the launch adds dynamic shared memory).
* NVRTC counts are of the device source compiled by NVRTC (CUDA 13.0 driver API) for sm_90; the judge builds the same source with `load_inline` / nvcc, so codegen can differ slightly.
* `ld.global` includes `ld.global.nc` (a subset); `atom` = `atom.*` + `red.*`; `cp.async` = `cp.async.ca/cg`; `wgmma` = `wgmma.mma_async`.
* A cp.async count says the pipeline exists, not that it is deep enough or that SASS keeps it (`LDGSTS` + `DEPBAR`): the `wait_group` values are in the notes column (N > 0 = copies stay in flight).
